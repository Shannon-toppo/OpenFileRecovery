# Open File Recovery

USB メモリと SD カードを主対象にしたデータ復旧ツール。Rust 製のコアの上に、
CLI と Tauri の GUI が載っている。設計と全体計画は [PLAN.md](PLAN.md) を参照。

MIT ライセンス。GPL/LGPL のコードは流用していない。外部バイナリ (ffmpeg など) にも依存しない。

## いまできること (Phase 6)

GUI と CLI の両方がある。**GUI は薄いラッパー**で、復旧の中身は全部 CLI と同じコード
(`ofr-core`) を通る。まず CLI で全機能を動かして検証し、GUI はその上に載せてある
(PLAN.md 8章)。

| コマンド | 内容 |
|---|---|
| `ofr list` | 接続されているデバイスの一覧。起動ディスクは選択不可として表示する |
| `ofr image` | 壊れかけメディアの吸い出し (ddrescue 方式の多段パス + mapfile による中断・再開) |
| `ofr scan` | FAT32 / exFAT の解析。生きているファイル、削除されたファイル、フォーマットで消えたフォルダを一覧する |
| `ofr restore` | 見つかったファイルをフォルダ構造ごと復元先へ書き出す |
| `ofr carve` | ファイルシステムに頼らないシグネチャカービング + Exif メタデータ抽出 |
| `ofr copy` | デバイスの中身をフォルダ構造ごと宛先へ写す (論理コピー / イメージ展開 + レポート) |
| `ofr repair` | 開けなくなったファイルを直す (JPEG / PNG / AVI / MP4) |

GUI からは同じことを、順番に進む 5 画面(デバイス選択 → やること → 実行 →
見つかったもの → 復元)で行う。表示は日本語と英語。

## ビルドと実行

### CLI

```bash
cargo build --release
```

生成物は `target/release/ofr`。生デバイスの読み込みには管理者 / root 権限が必要。

```bash
# デバイスを探す (権限なしで動く)
ofr list

# 吸い出す。出力先は必ず別のディスクにすること
sudo ofr image /dev/disk4 /Volumes/Backup/usb.img
```

Windows では管理者コマンドプロンプトから `ofr image \\.\PhysicalDrive2 D:\usb.img` のように使う。

```bash
# 吸い出したイメージを解析する (デバイスを直接指定してもよい)
ofr scan /Volumes/Backup/usb.img

# 見つかったものを復元する。復元先は必ず別のディスクにすること
ofr restore /Volumes/Backup/usb.img /Volumes/Backup/recovered

# ファイルシステムが全損している場合の最終手段
ofr carve /Volumes/Backup/usb.img /Volumes/Backup/carved

# いま入っているものを丸ごと、同じ構造で別のディスクへ写す
ofr copy /Volumes/USB /Volumes/Backup/mirror

# 戻したファイルが開けないときの最後の手当て
ofr repair recovered/IMG_0042.jpg repaired/IMG_0042.jpg
```

`ofr scan` は 2 段構えで探す。まずディレクトリツリーを普通に辿り、次にデータ領域を
全部舐めてルートから辿れなくなったフォルダを拾う。クイックフォーマットは FAT 表と
ルートしか消さないので、**フォーマット後の復元は後者が主力**になる。
拾ったフォルダは名前が分からない (名前は親フォルダ側にあるため) ので、
`Lost+Found/dir_00000003/` のような仮の名前でツリーに出す。

### `ofr image` の主なオプション

| オプション | 既定 | 内容 |
|---|---|---|
| `-m, --mapfile <PATH>` | `<出力>.map` | 取得済み/不良領域の記録。GNU ddrescue と互換 |
| `-r, --retries <N>` | 3 | 不良セクタのリトライ回数 (指数バックオフ付き) |
| `-b, --block-size <SIZE>` | `1M` | コピーパスの読み込み単位。エラー多発時は自動で縮小する |
| `--no-trim` / `--no-scrape` / `--no-retry` | — | 各パスを省く |
| `--unmount` | — | 開始前に `diskutil unmountDisk` する (macOS) |

中断 (Ctrl-C) しても mapfile が残るので、同じコマンドを実行すれば続きから再開する。
終了コードは 0 = 全域取得、1 = 未取得領域あり / 中断、2 = エラー。

### `ofr scan` / `ofr restore` の主なオプション

| オプション | 内容 |
|---|---|
| `--fs auto\|fat32\|exfat` | ファイルシステムの指定。既定は自動判定 |
| `--offset <SIZE>` | ボリュームの開始位置を直接指定する (パーティションテーブルが壊れている場合) |
| `--include <PATTERN>` | 名前かパスで絞る (`--include '*.jpg'`)。複数指定できる |
| `--status <LIST>` | 状態で絞る (`--status deleted,orphaned`) |
| `--no-orphans` | 全クラスタ走査を省く。速いが、フォーマット後のデバイスでは何も出ない |
| `--no-deleted` | 削除済みを探さない |
| `--tree` / `--json` | 表示形式 (`ofr scan`) |
| `--dry-run` / `--flatten` | 書き出さずに確認 / 階層を作らず平らに並べる (`ofr restore`) |

復元した項目には、信用してよい度合いを注記として出す。

- **連続配置と仮定**: FAT チェーンが失われているので、開始位置から連続していると
  仮定して回収した。断片化していたファイルはこの仮定で壊れる (`ofr repair` 行き)
- **使用中クラスタ N 個**: その領域は今も別のファイルに使われている。上書きされている可能性が高い
- **名前が不完全**: FAT32 で長い名前 (LFN) が残っていない削除ファイル。8.3 名の先頭 1 文字は
  仕様上どうやっても戻らないので `_` で埋めてある (exFAT では起きない)

終了コードは 0 = 全部できた、1 = 何も見つからない / 一部だけ / 中断、2 = エラー。

### `ofr carve`

フルフォーマット済み、あるいはファイルシステムが全損して `ofr scan` で何も出ない
デバイスからの最終手段。FS を一切見ず、デバイスを先頭から走査してファイル形式の
マジックバイトを探し、ヘッダのサイズ情報や終端マーカーから境界を計算して切り出す。

対応形式: JPEG, PNG, GIF, HEIC, MP4/MOV, AVI, WAV, MP3, ZIP (docx/xlsx/pptx を含む), PDF。

**元のファイル名は復元できない。** ディレクトリ情報を見ないので原理的に無理で、
名前は連番になる。Exif (JPEG) や `mvhd` (MP4) から撮影日時を拾えたものは
`20230415-142530_000042.jpg` のように日時が付く。名前が要るなら先に `ofr scan` を試すこと。

| オプション | 既定 | 内容 |
|---|---|---|
| `-a, --align <SIZE>` | `512` | ファイル先頭を探す境界。クラスタサイズ (`4096` など) が分かるなら指定すると速く正確になる |
| `-f, --formats <LIST>` | 全形式 | `jpeg,png,mp4` のようにカンマ区切りで絞る |
| `--max-size <SIZE>` | `4G` | 1 ファイルの上限 |
| `--start` / `--end` | — | 走査範囲を絞る |
| `--skip-truncated` | — | 終端を確定できなかったファイルを出力しない |
| `--dry-run` | — | 書き出さず、見つかるファイルの一覧だけを出す |
| `--report <PATH>` | `<出力>/carve-report.json` | 結果の JSON |

出力は形式ごとのサブフォルダ (`jpg/`, `mp4/` …) に分かれる。終了コードは
0 = 走査完了、1 = 中断、2 = エラー。

終端を確定できなかったファイルには「推定」が付く。この場合は次のシグネチャの手前まで
切り出すので、後ろに余分なデータが付いていることがある。断片化していたファイルは
`ofr restore` と同じく連続配置を仮定するため壊れる (`ofr repair` 行き)。

### `ofr copy`

「デバイスのデータとフォルダ構造をそのままコピーする」ためのコマンド。消えたものを
選んで拾う `ofr restore` とは向きが違い、**いま入っているものを丸ごと同じ形で移す**。

復旧元の指定で読み出し経路が決まる。

| 復旧元に渡すもの | 経路 | 使いどころ |
|---|---|---|
| フォルダ (`/Volumes/USB`) | OS のファイル API で読む論理コピー | OS がマウントできているデバイス |
| デバイス ID / イメージ | FAT32 / exFAT を直読みして展開 | マウントできないデバイス、`ofr image` で取ったイメージ |

壊れかけたメディアでは **`ofr image` でイメージを取り、そのイメージをコピー元にする**
のが推奨ルート。デバイスは触るたびに劣化する。

```bash
# マウント済みのデバイスから (論理コピー)
ofr copy /Volumes/USB /Volumes/Backup/mirror

# イメージから展開する (壊れかけメディアはこちら)
ofr copy /Volumes/Backup/usb.img /Volumes/Backup/mirror
```

| オプション | 既定 | 内容 |
|---|---|---|
| `--on-existing <MODE>` | `rename` | 宛先に同名があるとき `rename` / `skip` / `overwrite` |
| `--include-deleted` | — | 削除済み・孤立の項目もコピーする (デバイス / イメージのみ) |
| `-r, --retries <N>` | 2 | 読み込み失敗時のリトライ回数 (指数バックオフ付き) |
| `--chunk-size <SIZE>` | `1M` | 読み込み単位。壊れかけメディアでは小さくすると欠ける量が減る |
| `--no-zero-fill` | — | 読めない部分を埋めず、そのファイルを失敗扱いにする |
| `--no-timestamps` / `--no-empty-dirs` | — | 日時を移さない / 空フォルダを作らない |
| `--dry-run` | — | 書き出さず、何がコピーされるかだけ出す |
| `--report <PATH>` | `<宛先>/ofr-copy-report.json` | レポートの出力先 (人間向けサマリは同じ場所に `.txt` で並ぶ) |

1 ファイルの一部が読めなくても止まらない。リトライしたうえで、それでも読めない部分は
ゼロで埋めて残りを書き出し、埋めた量をレポートに残す。「読めた分は保存する」が
復旧ソフトとして正しい振る舞いで、開けなくなったファイルは `ofr repair` 行き。

完了時に宛先へレポートを 2 つ書く。`ofr-copy-report.json` が全ファイルの成否と
エラー内容 (GUI と後処理はこれを読む)、`ofr-copy-report.txt` が人間向けサマリ。
終了コードは 0 = 全部欠けなくコピーできた、1 = 欠け / 失敗 / 中断あり、2 = エラー。

中断した場合は `--on-existing skip` を付けて同じコマンドを実行すると続きから進む。

シンボリックリンクは辿らない (リンク先がデバイスの外へ出ると、復旧と関係のない
ファイルまでコピーしてしまうため)。宛先が復旧元フォルダの中にある場合は開始前に弾く。

### `ofr repair`

復元・カービング・コピーで拾ったファイルが開けないときの最後の手当て。
**修復元は絶対に書き換えない**ので、出力先には必ず別のパスを指定する
(同じパスを指定すると開始前に拒否する)。

```bash
ofr repair recovered/IMG_0042.jpg repaired/IMG_0042.jpg

# 同じ機器で作った正常なファイルがあると精度が上がる
ofr repair broken.mp4 fixed.mp4 --reference 同じカメラの正常な録画.mp4
```

| 形式 | 直せるもの | 直せないもの |
|---|---|---|
| JPEG | ヘッダ (SOI〜SOS) の破損、途中切断、末尾のごみ | 失われたエントロピー符号そのもの |
| PNG | CRC 不一致、チャンク長の破損、IEND 欠損、IDAT の部分破損 | 壊れた画素の中身 |
| AVI | idx1 の欠損・破損、RIFF / LIST サイズの破損、avih / strh の値 | 失われたフレーム |
| MP4 / MOV | moov の欠損 (参照ファイル方式)、mdat サイズの破損、末尾切断 | 参照なしでの完全な moov 再構築 |

| オプション | 既定 | 内容 |
|---|---|---|
| `-r, --reference <PATH>` | — | 同じ機器・同じ設定で作られた**正常な**ファイル |
| `--format <FMT>` | `auto` | 形式を指定する (`jpeg` / `png` / `avi` / `mp4`) |
| `--width` / `--height` | — | ヘッダが失われていて参照ファイルも無い場合の寸法 |
| `--fill <0-255>` | 128 | 欠けた画素を埋める値 (JPEG は仕組み上 128 固定) |
| `--no-verify` | — | 修復結果の検証を行わない |
| `--skip-intact` | — | 元から壊れていなかった場合は出力を書かない |
| `--report <PATH>` | — | JSON レポートの出力先 |

**参照ファイル**が効くのは、失われた情報が元のファイルのどこにも残っていない場合。
JPEG はヘッダ (量子化表・ハフマン表・寸法) を、MP4 は moov の構造とコーデック設定を、
AVI は hdrl を借りる。元のファイルに残っている情報の方を必ず優先するので、
参照を渡しても「別の写真になる」ことはない。

**切れたファイル**は、救えた所までを確定させて残りを埋める。JPEG はリスタート
マーカー (DRI) があれば、切れた位置以降の MCU を「係数が全部 0」として符号化し直す
(結果は中間グレーになる)。PNG は zlib を展開できた行までを残し、以降の行を埋めて
圧縮し直す。動画は実データの外を指すフレームを索引から外す。

**検証**は静止画と動画で違う。静止画は実際にデコードして寸法まで確かめる。
動画は「索引の全エントリが実データの中を指しているか」というコンテナ整合性までで、
実際に再生できるかは人間がプレイヤーで確かめること (ffmpeg に依存しないため、
デコードして確かめる手段を持たない)。

終了コードは 0 = 直った / 元から壊れていない、1 = 一部だけ直った / 直せなかった、
2 = エラー。何をどこまで直したか、何が残っているかは実行時に必ず表示する。

**期待値**: MP4 の moov 再構築は参照ファイルなしだと成功率が大きく落ちる。これは
市販ソフトを含めて原理的にそうなる。参照が無い場合は H.264 / H.265 の
エレメンタリストリーム (Annex-B) として取り出すところまでで、出力の拡張子は
`.h264` / `.h265` に付け替える。音声は復元できない。

## GUI (Phase 6)

Tauri v2 + Svelte。中身は CLI と同じで、`ofr-core` のジョブ API だけを叩く薄いラッパー。

```bash
cd app
npm install
npm run tauri dev      # 開発中はこれ
npm run tauri build    # インストーラ (dmg / msi / nsis) を作る
```

画面は 1 本道にしてある。復旧ソフトの利用者はトラブル中で余裕がないので、
選択肢を並べるより順番に進める構成のほうが向く(PLAN.md 7章)。

1. **デバイス選択**: リムーバブルデバイスの一覧。起動ディスクはグレーアウトして選べない。
   取得済みのイメージ (.img) を開くこともできる
2. **やること**: 「削除したファイルを探す」「フォーマットしたデバイスから探す」
   「壊れかけたデバイスを丸ごと吸い出す」「フォルダごとコピーする」
   「ファイル形式から探す(最終手段)」
3. **実行**: 進捗バー、速度、残り時間、エラー数。吸い出し中は領域マップを帯グラフで出す
   (取得済み / 不良 / 未試行)。中断してもそこまでの結果は残り、吸い出しは再開できる
4. **見つかったもの**: フォルダ構造のツリーと状態バッジ(無傷 / 削除済み / 孤立 / 破損)。
   選んだ項目は**サムネイルで中身を確認できる**。「連続配置と仮定」「使用中クラスタ N 個」
   のような注記もここに出る
5. **復元**: 復元先を選んで実行 → レポート。欠けたファイルには「修復を試す」ボタンが並び、
   参照ファイルを指定して `ofr repair` と同じ修復をかけられる

表示言語は日本語と英語で、右上から切り替える。文言は `app/src/lib/locales/*.json` にある。
**コアからは表示用の文字列を渡さない**(`deleted` のようなコードで渡して GUI 側で訳す)ので、
言語を足すときはリソースファイルを 1 つ増やすだけで済む。ただし解析中の警告や OS の
エラー文言だけは原文(日本語)のまま出る。訳しようがないものを無理にコード化するより、
原文をそのまま見せるほうが復旧作業の役に立つため。

### 権限

生デバイスの読み込みには管理者 / root 権限が要る。デバイスの**列挙は権限なしでも動く**ので、
GUI は「一覧は出るが開けない」状態になりやすい。そこで起動時に権限を調べ、足りなければ
画面上部で案内する。

**Windows**: 実行ファイルの manifest に `requireAdministrator` を入れてあるので、
起動時に UAC が出て昇格する。開発ビルドを直接叩いた場合だけ非昇格になりうる。

**macOS**: root だけでは足りない。**root と「フルディスクアクセス」の両方**が要る。

| 要るもの | 理由 | 与え方 |
|---|---|---|
| root | デバイスノードが `crw-r----- root:operator` | 画面上部の「管理者で起動し直す」 |
| フルディスクアクセス | 生ディスクへのアクセスが TCC で保護されている | システム設定 > プライバシーとセキュリティ > フルディスクアクセス |

手順は次のとおり(この順番で通ることを実機で確認した)。

1. アプリを起動して「**管理者で起動し直す**」を押し、パスワードを入力する
   (`osascript` の administrator privileges で自分自身を root として起動し直す)
2. 吸い出しを始めると「macOS の保護 (フルディスクアクセス) で止められている」と出る
3. その画面の「**システム設定を開く**」から、リストにこのアプリを追加してオンにする
4. アプリを起動し直して、1 からやり直す

**フルディスクアクセスの許可はアプリの署名 (cdhash) に紐づく。** ビルドし直すと許可が
外れるので、開発中は都度与え直すことになる。配布ビルドでは 1 回で済む。

片方だけだと次のようになる。エラー画面はこの 2 つを別のものとして出し分ける
(対処が正反対なので、混ぜると利用者が「管理者で実行し直す」を延々と繰り返すことになる)。

| 状態 | 返るもの | 画面の表示 |
|---|---|---|
| root でない | `EACCES` (os error 13) | 権限が足りない → 管理者で起動し直す |
| root だがフルディスクアクセスなし | `EPERM` (os error 1) | macOS の保護で止められている → システム設定を開く |

**フルディスクアクセスを与えたくない場合**は、ターミナルから `sudo ofr image ...` で
イメージを取り、GUI ではそのイメージを開けばよい。ターミナルは通常フルディスクアクセスを
持っているので `sudo` だけで通る。イメージの解析に権限は要らない。

この逃げ道は、権限問題の回避であると同時に**壊れかけメディアでの推奨フロー**
そのものでもある(PLAN.md 6章 4項)。

昇格して起動し直したプロセスは端末に繋がっていないので、ログは `/tmp/ofr-gui.log` に残す。
「昇格したのに動かない」ときはここを見る。

### 配布

`npm run tauri build` で macOS は `.dmg` と `.app`、Windows は `.msi` と NSIS の
インストーラができる。タグ (`v*`) を打つと GitHub Actions が両 OS 分を作って下書きの
リリースに置く(`.github/workflows/release.yml`)。

**署名と公証はかけていない。** MIT の OSS なので当面は未署名で配り、初回起動時に出る警告の
外し方を案内する方針にしてある(PLAN.md 10章)。

- macOS: 初回は右クリック →「開く」で起動する(Gatekeeper の警告を 1 度だけ承認する)
- Windows: SmartScreen の「詳細情報」→「実行」

## 安全のための決まり

- **復旧元デバイスには一切書き込まない。** デバイス抽象 (`trait Device`) に書き込み API を作っていない。
- OS の起動ディスクは復旧元として選べない。
- 出力先が復旧元と同じデバイス上にある場合はエラーにする。
- 壊れかけたメディアは、アクセスのたびに劣化しうる。**まずイメージを取り、以後はイメージを解析すること。**

## 対象外

- **物理障害**: コントローラが認識しない、OS からブロックデバイスとして見えない個体は
  ソフトウェアでは救えない。対象は「見えるが読み出しが不安定」な個体まで。
- **TRIM 済み領域**: 外付け SSD などで TRIM が効いた領域は復元できない。
  USB メモリと SD カードでは通常 TRIM が効かないので問題になりにくい。
- **断片化した削除ファイル**: FAT32 も exFAT も、削除時にクラスタのつながりが消える。
  連続配置と仮定して回収するので、断片化していたファイルは壊れた状態で復元される。
  該当する項目には注記が付く。
- **NTFS / APFS / ext4**: 対応しない。対象は FAT32 と exFAT (USB メモリと SD カードの標準)。
  ファイルシステムを問わない `ofr carve` なら中身は拾えるが、ファイル名は戻らない。
- **カービングでのファイル名**: 原理的に復元できない (上記 `ofr carve` 参照)。

## 開発

```bash
cargo test --workspace --all-features
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo fmt --all
```

CI (GitHub Actions) は windows-latest と macos-latest でテストと lint を回す。
壊れたメディアは CI に置けないので、不良セクタ・リトライ・再開は
`MockDevice` のエラー注入で検証している (`crates/ofr-image/tests/imaging.rs`)。

ファイルシステム解析のテストイメージは `ofr-testfs` が Rust だけで組み立てるので、
OS のフォーマッタを呼ばずに CI 内で完結する。生成物は本物の FAT32 / exFAT として
妥当なので、目視で確かめたいときはマウントできる。

```bash
cargo run -p ofr-testfs -- testdata/out
hdiutil attach -imagekey diskimage-class=CRawDiskImage -readonly testdata/out/fat32_deleted.img
```

カービングは全対応形式のサンプルを機械生成してテストイメージに埋め、正しい境界で
切り出せるか (中身が元と 1 バイトも違わないか) を検証している
(`crates/ofr-carve/tests/`)。CLI を手で試すためのイメージはこれで作れる。

```bash
cargo test -p ofr-carve --test carving -- --ignored write_test_image --nocapture
ofr carve testdata/out/carve-test.img /tmp/carved --align 4096
```

コピーは「不良セクタを注入したデバイスからコピーして、読めたファイルが全て宛先に揃い、
宛先の実ファイルサイズがレポートの記録と一致すること」を確かめている
(`crates/ofr-copy/tests/copy.rs`)。

修復は破損サンプル集で回帰テストしている (`crates/ofr-repair/tests/`)。静止画は
`image` クレートで実際にエンコードした本物を壊すので、修復結果をデコードして
元の絵と画素単位で比べられる。動画は構造だけを手で組み立てたものを使い、
索引が実データの中を指しているかを確かめる。サンプルは手元でも書き出せる。

```bash
cargo test -p ofr-repair --test repair -- --ignored write_samples --nocapture
ofr repair testdata/out/repair/no-moov.mp4 /tmp/fixed.mp4 \
    --reference testdata/out/repair/healthy.mp4
```

壊れたバイト列で panic しないこと (PLAN.md 6章 5項) は、乱数・切り詰め・ゼロ埋め・
長さフィールドの最大値を全形式に食わせて確かめている
(`crates/ofr-repair/tests/robustness.rs`)。

GUI が通る道は `crates/ofr-core/tests/jobs.rs` が画面なしでなぞる。「イメージを解析 →
結果を引く → 中身をプレビュー → 選んで復元 → 中身が元と一致する」まで通しで確かめて
いるので、GUI の不具合はたいていここで先に出る。フォルダを 1 つ選んだら中身も全部
復元されること、中断が効くこと、進捗が間引かれていることも見ている。

GUI 自体のビルドと型チェックは `app` で回す。

```bash
cd app
npm ci
npm run check   # svelte-check (型)
npm run build   # 型チェック + 本番ビルド
```

### 実機での手動確認 (CI で回せない項目)

1. `ofr list` に USB メモリ / SD カードが出て、容量と種別が OS の表示 (`diskutil list` /
   `Get-Disk`) と一致すること。ここは管理者権限なしで動くこと。
2. 起動ディスクが「選択不可」と表示され、`ofr image` が終了コード 2 で拒否すること。
3. イメージングが完走し (終了コード 0)、mapfile が全域 `+` の 1 ブロックになり、
   イメージ長がデバイスサイズと一致すること。生デバイスとイメージを数か所で突き合わせること。
4. 途中で Ctrl-C して再実行すると、`mapfile から再開する rescued=...` が中断時点の
   取得バイト数と一致し、取得済み領域を読み直さずに再開すること。

```bash
# macOS (root 権限が要る)
sudo ofr image /dev/disk4 /Volumes/Backup/usb.img
```

```powershell
# Windows (管理者権限の PowerShell で)
.\ofr.exe image '\\.\PhysicalDrive2' C:\usbtest\usb.img
```

出力先は必ず復旧元と別のディスクにすること (同一デバイスならエラーになる)。

Phase 2 で足したぶんの手動確認:

5. 実際の USB メモリ / SD カードで `ofr scan` が本物のファイル一覧を出すこと。
   容量・クラスタサイズ・ラベルが OS の表示と一致すること。
6. デバイス上でファイルを削除してから `ofr scan --status deleted` で出ること。
   `ofr restore` で戻したファイルが元と同じ内容で開けること。
7. デバイスをクイックフォーマットしてから `ofr scan` で `Lost+Found/` 以下に
   フォルダが出ること。復元したファイルが開けること。
8. 復元先に復旧元と同じデバイス上のフォルダを指定すると、終了コード 2 で拒否すること。

Phase 4 で足したぶんの手動確認:

9. マウント済みの USB メモリ / SD カードに対する `ofr copy /Volumes/USB <別ディスク>` が、
   Finder / エクスプローラで見える構造と同じツリーを作ること。ファイル数と合計サイズ、
   更新日時が一致すること。
10. 同じデバイスから取ったイメージに対する `ofr copy usb.img <別ディスク>` が、
    9 と同じツリーになること (2 つの読み出し経路で結果が一致すること)。
11. コピー中に Ctrl-C して `--on-existing skip` で再実行すると、書けていたファイルを
    読み直さずに続きから進み、最終的に 9 と同じツリーになること。
12. 読み出しが不安定なメディアで、一部が欠けたファイルがレポート
    (`ofr-copy-report.txt`) に列挙され、宛先の実ファイルサイズが JSON の
    `written` と一致すること。

Phase 5 で足したぶんの手動確認 (自動テストが再生確認まで踏み込めないため):

13. 実機で撮った写真を途中で切って `ofr repair` を掛け、出力が画像ビューアで開き、
    上半分が元の写真のまま見えること。
14. 録画中にカードを抜いて作った moov 無しの MP4 に、同じ機種・同じ設定で撮った
    正常なファイルを `--reference` に渡し、**プレイヤーで実際に再生できること**。
    映像の長さと画面の向き (縦位置で撮ったものが縦のまま出るか) を確かめること。
15. 参照ファイルを渡さない場合に `.h264` が出力され、期待値どおりの案内が
    表示されること。

Phase 3 で足したぶんの手動確認:

9. 写真の入った SD カードをフォーマットしてから `ofr carve` を掛け、写真が戻ること。
   撮影日時がファイル名に入り、画像ビューア / 動画プレイヤーで実際に開けること。
10. `ofr carve --align <クラスタサイズ>` の方が既定 (512) より速く、拾える数が
    変わらないこと。

7 は**実機でしか確認できない**。macOS のディスクイメージ (`hdiutil attach` した .img) を
`newfs_msdos` でフォーマットすると、イメージ側が TRIM を受けて全域ゼロになるため、
残骸が一切残らない。USB メモリと SD カードは通常 TRIM が効かないので実機では残る
(PLAN.md 10章)。イメージで試したいときは `cargo run -p ofr-testfs` が作る
`*_quick_format.img` を使うこと。こちらは実機のクイックフォーマットと同じく
FAT 表とルートだけを消してある。

Phase 6 (GUI) で足したぶんの手動確認。**1 番が Phase 6 の完了条件**:

1. フォーマットした SD カードを挿し、**GUI だけで**「フォーマットしたデバイスから探す」→
   写真をサムネイルで確かめて選ぶ → 別のディスクへ復元、が完了すること。
   復元した写真が画像ビューアで開けること。
2. 一覧で起動ディスクがグレーアウトし、選べないこと。復元先に復旧元と同じディスクを
   指定すると、始まる前に断られること。
3. 権限なしで起動したとき、上部に案内が出ること。macOS は「管理者で起動し直す」で
   パスワードを聞かれ、昇格した状態で立ち上がり直すこと。Windows は起動時に UAC が出ること。
   macOS では続けて、フルディスクアクセスを与えていない状態で吸い出しを始めると
   「macOS の保護で止められている」と出て、「システム設定を開く」から許可したうえで
   起動し直すと通ること (上の「権限」を参照)。
4. 吸い出し中に領域マップが伸びること。中断ボタンで止まり、同じ設定で始め直すと
   続きから進むこと。
5. 言語を English に切り替えると画面の文言が全部英語になること
   (解析中の警告と OS のエラー文言は日本語のまま出る。これは仕様)。
6. インストーラ (`npm run tauri build`) で作った `.dmg` / `.msi` から入れたアプリが
   起動し、上と同じことができること。

Phase 1 時点での確認済み: macOS 26 / KIOXIA TransMemory 57.7 GiB (163 MiB/s で完走)、
Windows / USB メモリ。
Phase 6 時点での確認済み: macOS 26 で dev / リリースビルドとも起動、`.dmg` (2.8 MB) の生成。
上の 3 (権限) は実機 USB メモリで確認済み — 「管理者で起動し直す」で root になり
(`geteuid() == 0` を `ps` で確認)、フルディスクアクセスを与えたうえで起動し直すと
生デバイスの吸い出しが始まる。`osascript` 経由で起動し直したプロセスにも、
アプリに与えたフルディスクアクセスは効く。
実機 SD カードでの通し確認 (上の 1) は未実施。

### クレート構成

`ofr-device` (デバイス) → `ofr-image` (イメージング) / `ofr-fs` (解析の共通土台) →
`ofr-fat` `ofr-exfat` (ファイルシステム) / `ofr-carve` (カービング) / `ofr-copy` (コピー) →
`ofr-core` (ジョブ API) → `ofr-cli` / `app` (GUI)。`ofr-carve` は FS を見ないので
`ofr-device` にしか依存しない。`ofr-repair` はファイルだけを相手にするので、
デバイスの読み出し口 (`FileDevice`) 以外には何も依存しない。

`ofr-core` は下のクレートを束ねる公開 API で、時間のかかる処理を全部「ジョブ」にしてある。
ジョブはスレッドで走り、進捗・見つけた項目・完了をイベントで流す。キャンセルは
`AtomicBool`。解析結果は「セッション」としてデバイスごと保持するので、結果ツリーの
プレビューと復元でメディアを開き直さずに済む。

**安全原則の判定はここに 1 つだけ置いてある。** 「起動ディスクを復旧元にしない」
「出力先が復旧元と同じデバイスなら拒否する」(PLAN.md 6章 2・3項) を CLI と GUI で
別々に実装すると、片方だけ直す事故が起きたときに取り返しがつかない。
CLI も GUI も `ofr-core::source` を通る。

CLI は解析クレートを直接呼び、GUI は `ofr-core` のジョブ API だけを呼ぶ。CLI が端末向けの
表示を細かく作り込んでいるのに対し、GUI は同じ情報をイベントで受けて画面にする。

PLAN.md の構成に対して `ofr-fs` と `ofr-testfs` を足してある。前者は FAT32 と exFAT で
中身が同じになる部分 (中間表現、32bit FAT 表、パーティション解析、復元処理) の置き場で、
どちらか一方のクレートに寄せると他方が依存する形になるため独立させた。
後者はテストイメージ生成専用 (`publish = false`)。

GUI (`app/src-tauri`) はコアの cargo workspace に入れていない。ビルドに Node と Tauri の
ツールチェインが要るので、CLI とコアの CI を軽く保つために分けてある。
